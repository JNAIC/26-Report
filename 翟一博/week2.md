# 主要学习内容

### • 把"脚本"改成"工具"（ask.py）

- 目标: 问题不再写死在代码里，改由命令行传入，同一份代码能反复用
- 做了什么:
  - 1. `argparse` 定义参数: `question` / `--system` / `--model` / `--temp` / `--stream` / `--dry-run`
  - 2. `nargs="*"` 让问题里可以带空格，不用加引号
  - 3. 流式输出: `stream=True` + `stream_options={"include_usage": True}`（不加这一项就拿不到 token 统计）
  - 4. `--dry-run` 只打印将要发送的 model / system / user，不真的调用——调提示词阶段先看再花钱
- 三次调用数据:
  - 1. `什么是token`: 37 / 37 token，1.30s
  - 2. `什么是RAG --stream`: 38 / 42 token，1.36s
  - 3. `解释embedding --system "你是教授，用比喻回答"`: 22 / 535 token，12.29s
- 结论: **成本和延迟主要由"输出长度"拉动**（同一个人问问题，输出涨 13 倍、耗时涨 9 倍），控制回答长度比精简提问更省钱

### • 第一次量化: 批量抽取 + 与标准答案比对

- 目标: 10 句输入 → 模型逐句输出 JSON → 与人工标注的标准答案逐字段比对，拿到可复现的准确率
- 做了什么:
  - 1. `样例输入.txt`: 10 句，后 5 句故意刁难（缺主谓 "排位"、缺时间 "明天打排位"、英文句、带条件的长句）
  - 2. `样例标签.json`: 给每句标注 `person` / `time` / `action` 三个字段的标准答案，**缺失必须标 null**
  - 3. `extract_tool.py`: 每次调用 `response_format=json_object` + `temperature=0`，输出四档状态与三项指标
- 四档判分（取代原来含糊的"OK"）:
  - 1. `[失败]` 调用或 JSON 解析出错
  - 2. `[缺键]` 少某个字段，结构就不对
  - 3. `[有空值]` 键齐但有 null —— 有时这才是正确答案
  - 4. `[OK]` 三个字段都有实际值
- 结果:
  - 1. 成功 10/10、键齐全 10/10、全字段有值 7/10、字段准确率 **28/30（93%）**
  - 2. 合计 1161 token，免费额度内 0 元

### • 复盘: 三个自己写出来的 bug

- 1. **类型假设太强**: `v in EMPTY` 用集合判断成员，模型把 `person` 返回成列表时抛 `TypeError: unhashable type: 'list'`
  - 修法: 空值判断按类型分支处理，并新增 `[类型异常]` 状态把"类型不合规"单独暴露出来
- 2. **统计口径混乱**: `n_ok += 1` 写在判分之前，判分崩了却仍显示"成功 100%"
  - 修法: 把"调用+解析"和"判分"拆成两段，各自计数
- 3. **分母陷阱**: 崩掉的那条被排除出分母，准确率从真实的 26/30（87%）虚高成 26/27（96%）
  - 修法: 汇总时同时输出"应有分母"和"实际参与比对的字段数"，不一致就明确警告
- 剩余 2 处不符的定性（比数字更重要）:
  - 1. `action` 期望"帮李雷查资料"、实际"在图书馆查资料" —— 标签太窄，模型没错
  - 2. `person` 期望 null、实际"三个人、我们组的两个人、外援" —— 标签本身有争议
  - 结论: **93% 可能已接近标注一致率的上限**；评估器本身也会错，必须逐条人工看

### • 实验产物与版本库的边界

- 目标: 仓库里只留"算不出来的东西"，可重生成的输出不要污染历史
- 做了什么:
  - 1. 建 `runs/` 目录，实验输出按 `日期_变量名.jsonl` 命名（如 `2026-11-10_修正判分与类型约束.jsonl`）
  - 2. `runs/` 与 `结果.jsonl` 加入 `.gitignore`；`结果.jsonl` 并从版本库移除
  - 3. 用 `Get-FileHash` 快速判断两次实验是否真有差异（哈希相同 = 白跑）
  - 4. 三次提交: `day0` 跑通调用 / `day1` 批量评估 / `chore` 清理可再生成的输出
  - 5. 密钥自查: `git ls-files --error-unmatch .env` 应报错；`git grep -E "sk-[A-Za-z0-9]{20,}"` 应无输出
- 一次真实教训: 四份结果文件哈希完全相同，但名字写着"基线 / 加类型约束"——**名字像做过对比，实际是同一次实验跑了四遍**
- 结论: 基线必须"改代码之前先存一份"；文件名写"当时改了什么"，不写"希望它是什么"

### • 踩过的坑

- 1. `pip install -r requirements.txt` 报找不到文件 —— 文件不在当前目录，`-r` 后面跟的是路径不是包名
- 2. `Get-Content .env` 输出乱码 —— 文件里的中文注释是 UTF-8，被 GBK 终端解码，文件本身没坏
- 3. 脚本打印 `¥` 和 emoji 直接崩 —— GBK 字符集里没有这些字符，输出统一改成中文 + ASCII
- 4. `extract.py` 没有产生记账 —— 记账逻辑写死在 `hello.py` 里，抽成 `usage_log.py` 公共模块后两个脚本共用
- 5. PyCharm 弹「IDE 内部错误」并点名 Windsurf 插件 —— 第三方插件与 minimap 线程冲突，禁用即可，与代码无关
- 6. `Rename-Item` 报"该目标表示路径或设备名称" —— 第二个参数只能写新文件名；要连路径一起写就用 `Move-Item`
- 7. 结果文件删了但 `git status` 还显示改动 —— 已跟踪的文件要先从索引移除，`.gitignore` 才生效
