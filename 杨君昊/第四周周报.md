# 第四周周报

本周完成华为鲲鹏实验：把同一份 C 源码分别放到鲲鹏 openEuler 和 x86 CentOS 两台云服务器上编译运行，对比两个平台的程序行为差异。

## 一、实验环境

两台华为云 ECS，规格都是 2 核 4G，操作系统分别是 openEuler 20.03（ARM64 架构，gcc 7.3.0）和 CentOS 7.2（x86_64 架构）。用 PuTTY 远程登录，用 WinSCP 上传源码，编译前先用 `gcc -v` 确认目标架构正确。

## 二、实验一：双精度浮点转整型溢出

原理是把一个接近 long 上限的数乘以 10，再强制转换回 long，结果必然超出范围。而 C 标准对这种情况不作规定，属于未定义行为，各平台自己决定怎么处理。

编译命令：鲲鹏用 `gcc -mabi=lp64 -march=armv8-a test.c`，x86 用 `gcc -m64 test.c`（手册写的 -ma64 是笔误）。

运行后发现两个平台完全不同。x86 上溢出后得到一个不确定值，即 0x8000000000000000，实际就是最小负数这种"哨兵值"，没有实际意义。鲲鹏上是饱和处理，上溢取 long 的最大值，下溢取最小值，结果始终在可表示范围内。两边的 sizeof(long) 都是 8，差异只出现在溢出时的取值上。

原因是两套指令集的实现选择不同：x86 的转换指令在超范围时写入固定哨兵值，ARM 采用饱和转换。移植时不能依赖这个结果，转换前要先判断范围。

## 三、实验二：char 类型的符号差异

C 标准没有规定 char 是有符号还是无符号。x86 上默认是有符号的，ARM 上默认是无符号的。

实验里用 `char ch2 = -1` 做对比：x86 上它是 -1，判为负数；鲲鹏上它被解释成 255，判为正数。同一个值，两台机器结论相反，而且都不会报错。

所以写跨平台代码时，凡是参与数值比较的字符变量，都要显式写成 `signed char` 或 `unsigned char`，不能靠编译器默认值。
